## 목표와 해석

교수님의 ‘수요일쯤 그럴듯한 화면을 역할을 나눠 올리기’라는 전달 내용을 기준으로, **연구실 개발환경에서 앱을 실행하고 PC 브라우저로 가게 조건→관련 공지→적용 조건/근거→원문 동선을 시연하는 버전**을 목표로 제안한다. 교수님이 전체 프런트/백엔드·DB·AI 시스템의 수요일 완성을 요구했다고 단정하지 않는다. 수요일 정확한 공유 시각은 팀이 확인한다. 모바일 우선 반응형 설계는 유지하며 외부 공개·휴대폰 실기기 외부 접속은 후속 확인 항목으로 남긴다.

이 실행안은 수요일까지의 단기 분담이며, 이전 착수팩v2의 ‘금요일 자료6건/AI3건/디자인 제안’ 작업지시를 이번 공유 버전 준비에 맞춰 갱신한다. 기존 전체 명세·최종 MVP 범위·정량 목표를 축소하지 않는다. 개발 진척·팀원의 가용시간·자료/도구 확보는 아직 미확인이다.

수요일까지 강명묵은 백엔드를 우선하고, 개발용 공식 공지 샘플 확보·전달은 남규민이 맡는다. 확인용 평가 자료/정답은 AI 튜닝과 계속 분리한다. 이번 임시 분담을 각25%의 실제 공수 균등이 확인된 것으로 보지 않는다.

## 연결 구조

```text
공식 공지 샘플 ── 김윤기: AI 추출·원문 대조
                              ↓ 검토된 데이터 파일
                  강명묵: 저장·조건 계산·API
                              ↓ 합의한 JSON 응답
                  이상헌: 모바일 화면·필터·상세
                              ↓
                  남규민: 통합 확인·배포 조율
```

사용자가 조회할 때마다 AI를 실시간 호출하는 구조를 수요일의 전제에 넣지 않는다. 원래 계획의 수집→AI 일괄 처리→사람 검토→저장→웹 표시 흐름을 유지한다. 자료가 아직 도착하지 않은 프런트/백엔드 작업은 같은 스키마의 가상 예시로 병렬 진행하며 화면에 가상임을 표시한다. 실제자료와 가상자료의 종류·건수를 구분한다.

## 오늘 먼저 맞출 것

1. 팀 저장소1개와 공통 기준 버전1개를 정한다. 각자 AI에게 별개의 전체 앱을 새로 만들게 하지 않고 같은 명세/폴더/예제 응답을 준다.
2. 폴더는 `frontend/`, `backend/`, `processing/`, `contracts/`로 나눈다. 프런트는 이상헌, 백엔드는 강명묵, AI 처리 코드는 김윤기가 맡는다. 공유 계약 수정은 먼저 팀에 알린다.
3. 기존 개발명세 I01/I02/I03와 D모델을 기준으로 `contracts/README.md`와 `contracts/examples/`의 입력·응답 예제를 함께 확인한다. 남규민이 취합하고 김윤기·강명묵·이상헌이 실제 입력/출력 타입을 확인한다. 예제 파일은 존재하며 실제 서비스 구현과 팀 검토 완료를 뜻하지 않는다.
4. 남규민은 자료원/세유형 샘플·연구실 개발환경의 실행 경로를 확인하고, 김윤기는 AI 도구 실행 가능 여부를 확인한다. 앱을 연구실에서 열어볼 수 있도록 실행 방법을 먼저 정한다. 운영 서버 변경은 수행하지 않는다.

> 이 저장소의 기존 명세와 contracts의 예제 응답을 기준으로 맡은 폴더만 구현해 줘. 현재 작업은 수요일 공유 버전이며, 담당 밖의 화면/API/스키마를 임의로 바꾸지 마. 변경이 필요하면 먼저 이유와 영향을 적어줘. 실행 방법·바꾼 파일·확인한 동작·미완료 항목을 남겨줘. 실제 AI/자료/배포가 없는 부분은 완료했다고 표현하지 마.

## 후속 외부 배포 경로 제안 — 수요일 연구실 시연과 구분

수요일은 연구실 개발환경에서의 실행을 우선 확인한다. 아래 외부 도메인 경로는 후속 후보이며, 연구실 내부 앱의 실제 접속 주소·실행 방식은 남규민이 확인한다.

희망 경로: **`https://aise.hknu.ac.kr/myai/team/`**. `/myai/team/`은 경로 후보이며 점유 여부·기존 경로와의 충돌은 확인하지 않았다.

읽기 조회로 확인한 사실: 소개 페이지가HTTP200을 응답했다. 외부 응답 헤더에는Nginx가 표시됐다. 내부 앱 프레임워크·프로세스·서버 설정·접근권한은 확인하지 않았다. 관리 로그인·설정 변경·업로드·배포는 하지 않았다.

현재의 도메인을 유지하면서 해당 경로를 앱으로 연결하려면 기존 웹서버의 경로 분기와 앱의 경로 설정을 맞추는 구성을 검토한다. 새 Apache/Tomcat을 추가 설치하는 것을 전제로 하지 않는다. 기존 루트 소개 페이지·관리 경로의 동작을 유지하는 변경안을 서버 관리자가 검토해야 한다.

- 프런트의 자산 기준 경로와 라우터 기준을 `/myai/team/`에 맞춘다. Vite는 중첩 배포의 `base` 설정을 제공한다. [Vite 공식 문서](https://vite.dev/guide/build.html#public-base-path)
- 외부 API 경로도 예를 들어 `/myai/team/api/v1/...`로 정하고, 프록시가 접두 경로를 제거할지 유지할지 백엔드와 합의한다. FastAPI는 프록시 뒤 경로 처리를 위한 `root_path`를 설명한다. [FastAPI 공식 문서](https://fastapi.tiangolo.com/advanced/behind-a-proxy/)
- Nginx의 경로별 proxy_pass 구성을 검토할 수 있다. 실제 기존 server/location 설정을 확인하기 전 적용용 설정 파일로 단정하지 않는다. [Nginx 공식 문서](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)

서버 변경 전 확인할 것은 실제 호스트/배포 경로, 기존 서비스/경로 소유자, 접근 방식, 사용할 Python 실행환경, TLS/프록시 구성, 재시작/원복 방법이다. 비밀번호·토큰·비밀키는 단톡/명세/소스에 넣지 않는다. 이번 요청의 허용 범위는 조회이며 운영 설정 변경과 실제 배포는 수행하지 않는다.

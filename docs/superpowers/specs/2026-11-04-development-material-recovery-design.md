# 개발용 추출 자료의 파일 복구 설계

## 목적과 현재 상태

B08·DB 명세의 선택 원본 백업을 신규 개발용17건까지 연결한다. 직전 단계는 실제 API 원본과 D05/D06을 저장하고16테이블206행의 SQL 복원을 확인했지만, 새 파일이 없는 상태에서 복원·재소비하지 않았다. 기존 Java/Python·표준 라이브러리·RecoveryDatabase·소유권 가드를 재사용한다. 새 제품 API·의존성·운영 백업 서비스는 추가하지 않는다.

## 선택과 불변 조건

- 기준은 develop `d2920b8`, stage38 manifest SHA `40f44d0e05299b87b3461680ae1e7790bf95c29566df8f1d069717a859d5ba51`이다.
- 명시한 stage38 `extraction-runs/`·`single-sources/`·`drafts/`만 선택한다. 합계321파일·55디렉터리·2606068바이트이며 원본17개와 registered17개를 모두 포함한다. 선택·실행·저장 JSON은 별도 증거로 고정한다.
- 파일 bytes/hash/크기·POSIX mode·정확한 구성과 실제 절대 경로를 보존한다. 등록본0400/0500·나머지0600/0700을 유지한다. symlink·비일반 파일·중첩 root/백업 부모·중복/링크/탈출 tar member·변조·기존 목적지는 거부한다. 배타적 rename은 기존 Python 저장 helper를 재사용한다.
- 현재206행 SQL은 stage38 `proof/storage-source-full.sql`, SHA `f1920df7918cc9ba7d68aec61ee90c4fb0e16c39cfc6b82b08b7dd199210b151`이다. 이전122행 SQL로 대체하거나 SQL 경로를 치환하지 않는다.
- 실제 키/API·gold·D09는 접근하지 않는다. 기존 자료·보호파일·사용자 .gitignore·main·다른 서비스는 보존한다. 새 소유 MySQL8.4.13·Java21·Python3.13만 사용하며 환경 주입을 제거한다.

## 복구 흐름

먼저 닫힌 세 경로를 tar/manifest로 백업하고 별도 위치에서 전체 member·bytes·mode를 대조한다. 이어 새 빈 전용 DB에 현재 SQL을 복원하고 전체16테이블206행/스키마·공개4테이블0과 기존 원본을 비교한다.

원본은 삭제하지 않고 새0700 보관 위치로 배타 이동한다. 이동 내역을 남기고 실패/중단 시 복귀한다. canonical 경로 부재와 다른 위치 재사용의 실제 거부는 성공/실패 D05 각1개·D06 1개로 확인하고 모든 선택 파일의 부재와 DB 전체 불변도 대조한다. tar에서 정확한 canonical 경로에 복원한 뒤 전체 D05 17개·D06 16개를 실제 JAR로 재실행한다. 상태·원래 실패·이미 등록/가져옴·206행/스키마·data SQL·HTTP 비노출을 유지해야 한다.

복원본을 사용한 검증 후 복원본은 별도 증거 경로에 보존하고 처음 보관한 원본을 원위치로 돌린다. 모든 원본/기존 manifest·mode와 타 서비스 상태를 다시 대조하고 자기 DB·프로세스·임시 credential만 정리한다. 강제 종료/전원 장애의 자동 복구는 보장하지 않으며 실제 이동 journal과 복귀 경로를 보존한다.

## 검증·인계

파일 경계와 실패 복귀의 작은 RED→GREEN, Java의 선택/경로/상태/환경 경계 시험, 실제 CLI/SQL/HTTP와 독립 읽기 전용 검증을 수행한다. 작성자 전체 리뷰와 마지막 새 문맥 전체 리뷰1회 후 유효 minor까지 해결한다. source PR→정확 CI/AI/새 사람 피드백→develop 병합→통합 gate를 거치며 main은 사람 검토다.

이번 범위는 새17건의 선택 파일 복구다. 기존 모든 root의 동시 유실·운영 접근/보존·RPO/RTO/PITR·권리/사람 검토·추출 정확도·40/20-20·D09·운영 등록/main/배포는 완료로 표시하지 않는다.

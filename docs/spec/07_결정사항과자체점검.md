> 이 파일은 전체 MVP 명세입니다. **11/3(화) 오후6시 인계·11/4(수) 연구실 PC 시연**의 우선 작업은 [화면 시연 작업 기준](../wednesday-screen-brief.md)을 따릅니다. 전체 기능·정량 목표는 유지합니다.

> **v1.1 기술 결정(2026-11-02): Flutter Web·Dart / Spring Boot·Java / MySQL / Python AI·계산.** 전체 기능·평가 목표를 유지합니다. 상세 연결은 [08 기술 구성](08_기술구성과연결.md), DB는 [09 DB 설계](09_DB설계와트랜잭션.md), 인원별 작업은 [10 WBS](10_인원별WBS.md)를 따릅니다.

### 대조 중 보완한 쟁점

1. 짧은 최신 계획서에 상세가 없는 ‘동시간대 묶기’를 원계획 기준 필수로 유지했다.
2. 날짜만 있는 사건과 명시 종일 사건을 별도 모델로 나눴다. 미상 시간이 종일 통제로 바뀌지 않는다.
3. 긴 도로를 끝점 하나로 선별해 누락하는 문제를 막기 위해 검토된 선분/정류장과 partial geometry를 정의했다.
4. 같은 사건 정정본뿐 아니라 한 문서에 함께 실린 여러 사건도 분할 그룹으로 묶었다.
5. 확인용 정답 교차검토와 프롬프트 개발 담당의 충돌을 줄이는 역할 조정안을 명시했다.
6. 자동 추출 평가와 사람 수정 후 카드 품질, 최초 평가와 재시험, 전체 참여와 유효 시간 비교 인원을 분리했다.
7. 과거 재현에 이후 정정을 소급하는 오류를 막도록 knowledge cutoff와 당시 자료 확보 수준을 표시했다.

## 팀장이 마지막으로 답하면 되는 질문

1. **현재 진행 상태와 시간:** 이미 구현한 코드, 모은/검토한 공지 건수, RT 진행 여부, 팀원별 이번 주 가용 시간을 알려줄 수 있는가?
2. **구역·자료·도구:** 정한 시범 구역/5지점/공식 자료원, 지원 AI 계정·API, 사용 가능한 배포 환경이 있는가?
3. **현장 운영:** 센터가 확정한 RT·실증·성과회 날짜와 현재 참여 가능 사용자/전문가, 기록 보존 기준이 있는가?

위 답을 받으면 기능 범위를 줄이지 않고 W별 담당 일정·자료 확보 계획·실증 예약 순서를 구체화한다. 문서 자체는 이 답을 기다리지 않고 개발 계약 검토와 가상 fixture 기반 구현을 시작할 수 있는 수준으로 구성했다.

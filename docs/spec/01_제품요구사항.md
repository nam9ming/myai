# 01. 제품 요구사항

> 이 파일은 전체 MVP 명세입니다. **11/3(화) 오후6시 인계·11/4(수) 연구실 PC 시연**의 우선 작업은 [화면 시연 작업 기준](../wednesday-screen-brief.md)을 따릅니다. 전체 기능·정량 목표는 유지합니다.

> **v1.1 기술 결정(2026-11-02): Flutter Web·Dart / Spring Boot·Java / MySQL / Python AI·계산.** 전체 기능·평가 목표를 유지합니다. 상세 연결은 [08 기술 구성](08_기술구성과연결.md), DB는 [09 DB 설계](09_DB설계와트랜잭션.md), 인원별 작업은 [10 WBS](10_인원별WBS.md)를 따릅니다.

기준: [00_목차](00_목차.md)의 S1~S8·U1. [확정 요구]와 목표는 아래 표에 표시하며, 상세 구현은 [설계 제안]이다.

## 문제와 검증할 가설

[확정 요구] 안성 원도심 시장 인접 구역의 소상공인이 공사·행사·교통 변경 공지를 가게의 위치·영업시간·대상 조건에 맞춰 확인하도록 돕는다. 공공기관의 공식 서비스가 아닌 안성맞춘팀의 시민 실증 시제품이다.

| 가설 | 확인 방법 | 반대 결과가 나왔을 때 |
|---|---|---|
| H1 게시 위치와 표현이 달라 탐색에 부담이 있다 | 최근 실제 확인 경험·사용 채널·막힌 단계 인터뷰 | 불편이 적었다는 의견도 보고하고 화면의 효용을 재검토 |
| H2 날짜·위치·대상·예외를 함께 제시하면 확인이 쉬워진다 | 게시판+지도와 시제품의 동등 과제 비교 | 속도만 좋아지고 정확도가 떨어지면 성공 주장 금지 |
| H3 AI가 단순 규칙보다 비정형 조건을 잘 추출한다 | 동일 확인 자료의 규칙/AI 자동 결과 비교 | 필드별 열위와 사람 수정 부담을 보고 |
| H4 모바일에서 짧은 동선이 유용하다 | 실제 기기 조작·원문 이동·조건 이해 관찰 | 막힌 단계·글자/필터/상태 설명을 개선 |

공공 공지가 존재한다는 사실은 반복적 매출 피해나 수요 규모의 증거가 아니다. 사용자 수요·성과는 아직 검증되지 않았다.

## 사용자와 시나리오

| ID | 상황 | 사용자 행동 | 올바른 결과 |
|---|---|---|---|
| UC1 | 손님에게 접근 변경을 안내하려는 점포 운영자 | 기준 지점·영업시간 선택 → 공사/교통 → 방향·구간 확인 → 원문 | 가까운 사건과 실제 통행 제한을 구별하고 적용 대상 확인 |
| UC2 | 배달·입고 시간을 확인하려는 운영자 | 야간 영업 입력 → 관련 시간대와 정류장·도로 예외 확인 | 자정 통과 포함; 미상 시간은 종일 제한으로 해석하지 않음 |
| UC3 | 주변 행사 준비를 하는 운영자 | 행사 후보와 같은 시간의 공사·교통 변경 함께 확인 | 동시 발생 근거와 각각의 원문 제공; 방문객·매출 예측 없음 |
| UC4 | 센터에서 체험하는 시민 | 로그인 없이 5개 시험 지점 중 선택 → 과거 사례 모드 | 재현 기준일을 계속 표시; 실제 상인 참여 실적으로 세지 않음 |
| UC5 | 팀 자료 담당 | 수집 → AI 추출 → 원문 대조 → 수정 → 승인 → 공개 | 출처와 버전을 추적할 수 있고 미검토 값이 자동 공개되지 않음 |

지점 5곳은 실제 참여 점포 5곳이 아니다. 정확한 시범 구역·명칭·좌표는 확인 필요다. 현장 인터뷰는 세 유형과 세 활용 방향의 안내 항목·과제를 정교화하는 데 사용한다.

| ID | 요구 / 우선순위 | 근거 | 화면·데이터·인터페이스 | 완료 기준 |
|---|---|---|---|---|
| R01 | 시범 구역 1곳·시험 지점 5곳 선택, 로그인·매출 입력 없음 / P0 | S1 p2, S2 p1, U1 | S01, D01, I01 | T01: 검증된 5지점·구역 표시, 미등록 지점 거절 |

| R16 | 연결 실패·빈 결과·상태 미확인·복구 안내 / P0 | S1 p4, U1 | S01~S04/S10, D07, I01~I03 | T20/T23: 실패를 0건으로 표시하지 않음 |

R09는 복잡한 생성형 브리핑과 다르다. 이미 계산한 사건 시간의 교집합과 링크를 묶는 기능이므로 원래 핵심 범위에 유지한다.

P1: 지도 시각 꾸미기·자동 발송·복합 브리핑·시설 운영 변경은 S1의 핵심 이후 순서를 유지한다. PWA 설치는 U1의 선택 검토 항목으로 추가했으며, 회원 시스템·네이티브 앱·상시 자동 수집은 새 필수 기능으로 추가하지 않는다. 임의 주소/GPS·개인화 추천·푸시도 이번 기본 구현에 요구하지 않는다.

## 기능과 별도로 평가할 목표

| ID | 목표 [확정 요구] | 보고 단위·판정 |
|---|---|---|
| M01 | 공식 공지 40건, 개발 20·확인 20 | 고유 공지 문서 수와 고유 사건 수 병기; 재게시·정정 관계 명시 |
| M02 | 핵심 필드 일치율 90% | 정답 있는 필드의 자동 추출 일치율; 누락 오답·생성 별도, 사람 수정 후와 구별 |
| M03 | 공개 카드 원문 링크·최종 확인 시각 표시율 100% | 공개된 모든 상태 카드 포함; 연결 성공은 별도 검사 |
| M04 | 사용자 6명 목표·최소 3명 평가 추진 | 실제 모집·시작·완료·중단 인원 및 상인 여부 보고 |
| M05 | 개인별 탐색 시간 단축률 중앙값 20% | 양쪽 정확 완료 비교 쌍만 계산; 유효 인원·실패·누락 함께 보고 |

기능 인수 통과가 M02·M05 달성을 뜻하지 않는다. 목표 미달을 숨기거나 분모·과제를 사후 변경하지 않는다. 실제 자료·사용자가 부족하면 확보량과 미달 이유를 밝히고 모집/자료 확보를 계속 추진한다. 승인 없이 목표를 낮추지 않는다.

## 문서 차이의 처리

| 차이 | 해석과 적용 |
|---|---|
| S1의 초기 수요에 따라 범위 좁히기, S5의 Scope-down 권고 | U1과 최신 S2의 계획 유지 결정 적용. 세 유형·핵심·목표는 유지하며 안내 항목/작업 순서를 구체화 |
| S2에는 동시간대 묶기 상세가 축약됨 | S1의 명시적 기능을 삭제하지 않고 R09 유지 |
| S1 10월 회기 계획 vs 현재 11월 2일 | 과거 계획은 실적이 아님. 실제 진척 미확인, 06에서 완료 게이트 중심 재계획 |
| 시민 3~5·전문가 1~2 권장 vs 팀 6/최소3 | 팀 목표 유지, 전문가 자문 별도; 시민과 전문가 중복 합산 금지 |
| S3 서식6 수시/정기 vs S4/S7 종료 종합 1회 | 수시 기록 유지, 제출 주기는 센터 확인 |
| S6 결과 증빙 1장 vs S3 서식5 2장 | 동의·비식별 범위에서 2장 이상 준비 제안 |
| 팀 예산 100만원 vs 일반 지원 100~150만원 | 100만원은 팀 계획. 승인·지급 조건은 확인 필요; 원계획이 인용한 안성 공문 원본은 미제공 |

프로그램 양식의 예시 인명·실적·행사 날짜는 팀 자료로 옮기지 않는다. 셰르파 내역서는 팀의 7종 산출물과 별개다.

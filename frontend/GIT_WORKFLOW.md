# 프론트 변경 공유 규칙

2026-11-17 사용자 지시: 주요 프론트 변경은 검증한 뒤 작업 브랜치에 커밋·공유한다. 사용자 화면을 제어하지 않으며 기존 사용자 변경과 다른 담당 코드를 보존한다.

## 주요 변경마다 적용할 순서

1. `git status`, 현재 브랜치·원격, 최신 원격 커밋을 확인한다. 윤기 등 다른 담당 변경에서 API·필드·오류·실행 환경·명세의 영향을 먼저 검토한다.
2. 통합 기준은 `develop`, 공유 브랜치는 `frontend/yeogi-it-flutter`다. 미커밋 변경을 보존하고 충돌을 검토해 최신 기준을 반영한다. 원격 브랜치가 다른 작성자의 작업으로 진행됐으면 먼저 비교하며 덮어쓰지 않는다.
3. 소스·자산 검증, format·analyze·관련 단위/위젯·빌드를 수행한다. API 변경은 계약 fixture/실제 HTTP 검증을 구분한다. 기존 Windows 공통 테스트 실패는 기존 실패로 기록하고 통과했다고 쓰지 않는다.
4. `git add .` 대신 이번 작업의 파일을 명시해 stage한다. SDK·캐시·빌드·입력 ZIP·비밀값·개인 자료는 제외한다. staged diff·파일 크기·변경 경계를 확인한다.
5. 기능 단위의 영어 Conventional Commit을 만든다. 제목은 명령형·50자 이내·마침표 없음이며 AI 서명 트레일러를 넣지 않는다. major change를 임의 파일 저장 이벤트 전체와 동일시하지 않는다.
6. 원격 head를 재확인한 뒤 일반 fast-forward push 또는 같은 부모의 새 브랜치 생성을 수행한다. CLI 인증이 없으면 연결된 GitHub 앱으로 blob/tree/commit을 생성할 수 있다. 이때 원격 tree SHA와 로컬 `git write-tree`가 일치하는지 검증하고 같은 커밋으로 로컬을 동기화한다.
7. 원격 SHA·부모 관계·변경 파일·로컬 tracking 상태와 CI 결과를 확인한다. CI 대기·실패·부분 검수는 그대로 기록한다.

강제 push·이력 재작성·사용자 파일 강제 초기화·다른 담당 코드 일괄 교체·main 직접 push를 하지 않는다. develop/main 병합과 배포는 이 자동 공유 범위에 포함하지 않는다. 개발 세션에서 수행하는 주요 프론트 변경에 적용하며, 사용자 파일 전체를 감시해 자동 커밋하는 서비스를 설치하지 않는다.
